# Multi-task staging implementation and release gate

This branch combines the existing shared Valkey infrastructure and stateless proxy renderer with the actual Celery-enabled ECS task. It adds a separate singleton worker/Beat task definition and read-only live capacity gates. The workflow intentionally fails rather than claiming success when requirements are not met.

Order of operations (do not skip gates):
1. Verify AWS account plan permits ElastiCache, pricing and all-in monthly forecast <= R1100 (including VAT, compute, ALB, data, snapshots and secrets). Do not create chargeable resources on assumptions. The shared Valkey provisioner rejects the FREE plan and an unreviewed budget. It creates only the private TLS cache and scoped secret access, not traffic changes.
2. Confirm private cache reachability and rediss certificate validation from a disposable isolated task. Check the current queues, scheduled/reserved tasks, active jobs, unacknowledged deliveries and outbox. Quiesce producers and stop the old Beat before draining workers; reconcile and preserve pending jobs, never flush the broker. Take backup and test restore. A rollback must preserve the same shared broker, not revert to a stale task-local queue.
3. Render the two definitions from the live six-container task, test ARM64 proxy and jobs startup. Register definitions only after queue migration, backup, capacity and maintenance approval. Deploy singleton jobs with desiredCount=1 and stop-before-start policy (minimumHealthyPercent=0, maximumPercent=100) so rolling deployments never intentionally overlap Beat. A scheduler lock/fencing test is still required before production. Web tasks must never run Beat. Validate worker, scheduler and outbox behavior before reopening producers.
4. Remove the old single-host service placement restriction only after testing on both hosts. Verify actual CPU, memory, ENI and subnet capacity for four web tasks plus jobs and safe rollout headroom; reservations alone are not measured peak usage. The audit reports conservative ENI slots and does not promise four-task capacity.
5. With approved capacity, verify four healthy tasks of the same revision behind ALB, then use the existing configure-staging-service-scaling.sh. Recheck scale-out/scale-in and 2-4 limits. The audit fails if gates are unmet.
6. Run the manual bounded read-only k6 smoke after four healthy replicas. This is NOT a load capacity certification; capture per-target traffic evidence from trusted ALB logs or private per-task metrics, then progressively test 50/100/250+ VUs with CPU, memory, error and latency limits. No booking/payment writes are allowed in this smoke.
7. Verify CloudWatch alarms, native blue-green routing and real rollback in staging; confirm shared-state and adequate simultaneous-revision capacity. The existing production release remains untouched until separate AWS production infrastructure, backup/restore, immutable artifact publication, sandbox payments/notification acceptance, load and rollback evidence are all verified.

No resource creation or production traffic changes occur from the push-triggered workflow. Existing one-task staging stays in place. The public test IP is staging only.
