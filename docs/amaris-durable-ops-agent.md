# Amaris Durable AI Operations Agent — integration design

Status: **design / not deployed**. This document adapts the human-in-the-loop pattern from [rahulwagh/trigger-dev-ai-agent](https://github.com/rahulwagh/trigger-dev-ai-agent) to Amaris's **Render + Django + Supabase + GitHub** infrastructure. It does **not** introduce Kubernetes or permit unattended production changes.

## Operating boundary

- This is **not** the public student-facing Amaris Assistant. Its operations chat must be exposed only to authenticated **Django superusers**. Do not trust a frontend role claim; enforce authorization at every server endpoint, tool invocation, approval and event-stream subscription.
- Default capability: read-only, explicitly allowlisted diagnostics. Deny all commands/actions unless the backend implements their precise allowlist entry.
- Never install kubectl, provision an EKS cluster, or run arbitrary shell commands to reproduce the example.
- Student/tutor PII, emails, private media, Supabase credentials, payment passphrases, JWTs, API keys, bank account details and complete database rows must never be sent to the model or shown in logs. Redact known secrets and limit log excerpts *before* model ingestion.
- Keep paid Trigger.dev resources **disabled** pending cost approval. No paid monitoring infrastructure is provisioned by this change.

| Notifications | Private Django Admin incident inbox; email alerts only when configured and verified |

## Workflow

1. Superuser creates an incident thread; Django stores a thread ID and creator ID.
2. On each chat message the server checks superuser access, persists the message, and queues a unique investigation job. Messages and job state are recoverable after refresh/redeploy.
3. The agent fetches read-only evidence using scoped API clients. It must distinguish *unknown/unconfigured* from *healthy*. It does not invent error rates, logs, restarts or prices.
4. If remediation is warranted, the agent creates an **immutable proposal**, never directly invokes a write-capable tool. Present exact target, action, preconditions, estimated scope, rollback and evidence.
5. A human superuser can approve or deny a particular proposal version. Store actor, timestamp, expiry, evidence digest, target and action-parameter digest in a database transaction.
6. A **separate execution service** re-authorizes the operator, validates approval, re-checks target/preconditions, verifies action allowlist and environment, consumes the single-use approval atomically, and writes an append-only audit event. Reject stale, replayed or mismatched approvals.
7. Production changes require a **fresh, explicit approval per action**, not a blanket auto-remediation setting; use existing GitHub checks, backup gates and production-release safeguards. For a database migration or irreversible action require the established manual release path rather than an AI button.
8. Always record the outcome as `succeeded`, `failed`, `expired`, or `unknown`; never represent a timed-out remote request as successful without corroboration.

## Initial tool allowlist (READ ONLY)

- `health_probe`: GET fixed Amaris health endpoints; HTTPS only, no redirects to unapproved domains, response cap, request timeout.
- `render_recent_deploys`: query fixed service IDs for staging and production, using a token scoped to read resources only.
- `render_recent_logs`: short time-bounded, count-limited, scrubbed logs; no broad full-log extraction.
- `github_workflow_status`: list Actions checks for selected repository and commits.
- `supabase_connectivity`: query only health/connection state via backend; **no SQL generated by an LLM**.
- `monitoring_snapshot`: aggregate metrics via a server-controlled allowlist of fixed Prometheus expressions; unavailable if not configured.

Initial writes: **NONE**. A follow-up implementation may expose individually allowlisted operations only after threat modelling, integration tests and human approval. Do not grant the Trigger worker blanket GitHub/Render/Supabase write tokens.

## Schema to implement with new migrations (NOT created by this design PR)

- `OpsConversation`: UUID, creator, created/updated timestamps, last sequence, archived flag.
- `OpsMessage`: conversation FK, sequence, role, structured content with redaction, created timestamp.
- `OpsInvestigation`: UUID, conversation FK, status, Trigger run ID (nullable), started/completed timestamps, summary.
- `OpsEvidence`: investigation FK, source type, source locator, observed timestamp, sanitized excerpt, digest.
- `OpsProposal`: UUID, version, target environment, action name, canonical args digest, evidence digest, preconditions, rollback, status, expiry.
- `OpsApproval`: proposal/version FK, approver user FK, decision, timestamp, expiry, single-use nonce digest. Unique constraint on proposal version; approvals cannot be edited.
- `OpsActionAudit`: proposal FK, actor, request/idempotency key, precondition checks, execution outcome, timestamp, response digest.

Use transactional row-level locking and database uniqueness constraints for approval consumption. Enforce retention controls and audit integrity.

## Integration surfaces

Django routes under `/admin/ops-agent/` via an admin-protected view for the UI. Optional `/api/internal/ops-agent/` REST endpoints must use equivalent server-side authorization plus CSRF/session checks; do **not** expose Trigger API keys, Render tokens, GitHub tokens or Supabase service-role keys to the browser.

Never allow an arbitrary URL, command, SQL string, deployment hook, GitHub workflow name, or Kubernetes context supplied in chat to become a tool argument without a strict server-side allowlist.

## Acceptance gates

1. Anonymous, student, tutor, ordinary staff, and deactivated users get 403/redirect and cannot receive stream events.
2. A read-only probe cannot invoke mutating APIs and redacts secrets/PII before model context/logs.
3. Chat survives refresh and a worker restart without duplicating a tool action.
4. Proposed action has no effect before approval; deny/expired/stale/mismatched/replayed approvals never execute.
5. A changed target SHA/service state invalidates approval. A concurrent second executor cannot reuse the approval.
6. Staging exercises healthy/unhealthy/timeout/unconfigured Render, GitHub, Supabase and health-probe cases using mocks; no real payments.
7. No release to production before CI, new migrations on staging, rollback test, genuine production backup and authorized release approval.
8. Budget consent is required before any paid Trigger.dev plan or worker is started.

## Delivery plan

- Phase 1: Django persistence models, superuser-only admin UI, fixed read-only health and GitHub/Render probes, security tests.
- Phase 2: durable Trigger.dev adapter with pinned, verified SDK version; session resumption, retries, event replay and secure secrets.
- Phase 3: proposal/approval workflow, immutable audit log, execution service initially dry-run only, adversarial tests.
- Phase 4: staging E2E, privacy/cost review, production backup, formal release approval; optional narrow mutations in later PRs.

**This PR contains design documentation only; no live AI chat, Trigger.dev task, database migration, credentials or deployments are added.**
