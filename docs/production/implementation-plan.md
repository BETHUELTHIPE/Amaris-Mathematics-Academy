# Amaris Mathematics Academy — Production Implementation Plan

_Last updated: 2026-09-23 (SAST)_

## Goal

Deploy a separate production Django/Celery data plane for the live student frontend at:

- Frontend: https://amaris-mathematics-academy-live-students.onrender.com
- Production API target: https://amaris-production-web.onrender.com

The production data plane must use isolated paid Render resources, Supabase Auth/Storage, server-verified PayFast processing, durable background jobs, and immutable invoice PDFs.

## Production architecture

### Already provisioned

- PostgreSQL 17: `amaris-production-postgres` — Render `basic_1gb`, Frankfurt, 5 GB
- Redis broker: `amaris-production-broker` — Render `starter`, Frankfurt, noeviction + journal/snapshot
- Redis cache: `amaris-production-cache` — Render `starter`, Frankfurt, allkeys-lru
- Supabase private student files bucket: `Amaris Mathematics Academy`
- Supabase private CMS bucket: `amaris-cms-files`
- Student Storage RLS: authenticated users restricted to their own UUID prefix
- Automatic invoice PDF generation/archive code
- Deterministic invoice path: `<student-uuid>/invoices/INV-<payment-reference>.pdf`
- Invoice SHA-256 + storage path + generation timestamp audit fields
- Retry/recovery queue for missing invoice PDFs

### Production services to create from render.yaml

1. `amaris-production-web`
   - Django 5 / ASGI / Gunicorn
   - standard plan
   - Frankfurt
   - migrations before release
   - readiness health check
   - production Postgres, production cache, production broker
   - Supabase Auth and private S3-compatible Storage
   - PayFast live configuration

2. `amaris-production-critical-worker`
   - Celery queues: critical, default
   - automatic verified invoice PDF archival
   - payment and integration retries

3. `amaris-production-notification-worker`
   - Celery queue: notifications
   - transactional mail/outbox

4. `amaris-production-beat`
   - reconciliation
   - invoice archive recovery
   - scheduled tasks

## Production secret bindings

The following values are server-only and MUST be set in Render, never committed:

- `SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_STORAGE_S3_ACCESS_KEY_ID`
- `SUPABASE_STORAGE_S3_SECRET_ACCESS_KEY`
- `PAYFAST_MERCHANT_ID`
- `PAYFAST_MERCHANT_KEY`
- `PAYFAST_PASSPHRASE`
- SMTP credentials / sender
- Django secret key (generated by Render)

Resource connection strings must be linked by Render references, not copied into GitHub:

- `DATABASE_URL` -> `amaris-production-postgres`
- `DJANGO_CACHE_URL` -> `amaris-production-cache`
- `CELERY_BROKER_URL` -> `amaris-production-broker`
- `CELERY_RESULT_BACKEND` -> `amaris-production-broker`

## Deployment sequence

1. Provision isolated production Postgres, Redis broker, and Redis cache.
2. Create production Django web and workers from `render.yaml`.
3. Set server-only secrets.
4. Run migrations on production Postgres.
5. Verify `/health/ready/`.
6. Verify Supabase JWT authentication against a synthetic account.
7. Run private Storage write/read/delete probe.
8. Run Django -> Postgres, Redis and Celery integration checks.
9. Exercise a sandbox/mock payment notification only; never make a real payment during smoke testing.
10. Verify a synthetic paid invoice generates a PDF and archives it in the synthetic student's UUID folder.
11. Set the live frontend `CMS_API_URL` to production API.
12. Redeploy frontend.
13. Run safe post-deploy smoke: homepage, login, registration, courses, API health, static assets, authenticated dashboard.
14. Run synthetic authenticated student journey: profile -> course -> lesson -> progress -> payment-status read.
15. Observe logs/metrics.
16. Roll back frontend API target and backend release if any critical health check fails.
